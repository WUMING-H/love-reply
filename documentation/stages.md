# 阶段：为什么是闸门，不是参数

## 1 一个参数化的诱惑

最直接的做法是把阶段当成一个系数：给每条候选算分，阶段影响权重。

```
score = 0.5 × 相关 + 0.3 × 语气匹配 × stage_weight + 0.2 × 推进度
```

这个方案能跑，但会稳定地在最该拒绝的时候给出候选。因为打分是**连续**的：`stranger` 阶段给一句邀约，算出 0.42，不算高但也不是零，排序后仍然可能进前三。用户看到三条候选，其中一条明显不该出现——这不是精度问题，是**类别错误**。

所以我们用闸门：`stranger` 阶段禁用 `advance`，不是"降低权重"，是**不允许出现**。

打分的错误是"不太合适"，闸门的错误是"根本不出现"。在时机问题上，后者才是对的。

## 2 为什么阶段优先于目标

目标和阶段可能冲突：你想三个月内定下来（目标推进），但你们正在冷战中（阶段禁推进）。

这时候如果按"目标优先"处理，会给出一个激进的候选，而它在当下必然失败。如果按"阶段优先"，你会得到一句"先把上次那件事说清楚"——目标没有推进，但也没有被伤害。

**阶段描述的是现实，目标描述的是愿望。** 现实先于愿望，这是唯一可行的顺序。

唯一的例外是 `exit`。当目标是收尾时，维持关系不再是约束——你不需要她继续喜欢你，只需要把话说完整。所以阶段闸门在 `exit` 下放宽。这是有意开的唯一一个口子。

## 3 六档是怎么切的

切的依据不是感情的深浅，是**可用的手段**。两个相邻阶段之间，至少有一类策略从"可以用"变成"不能用"，否则就该合并。

| 边界 | 什么变了 |
|---|---|
| `stranger` → `warming` | 出现 `substantive`：可以给实质内容，不再只是接话 |
| `warming` → `dating` | 出现 `advance`：可以主动推进，不再只是留退路 |
| `dating` → `couple_early` | `hold` 被禁：不能再用沉默处理问题 |
| `couple_early` → `couple_stable` | `advance` 变成罕见：默认不推进，除非真有下一步 |
| 任意 → `repairing` | `advance` 被禁、`hold` 被允许、细节密度降到最低 |

三处反直觉的设计，各有理由：

**`stranger` 禁 `hold`。** 留白的前提是有存量。刚加上就消失，不是克制，是归零。

**`dating` 禁 `hold`。** 这个阶段的不确定性最高，沉默会被读成没兴趣。宁可给一条明确的、可能被拒的话。

**`warming` 的 `advance` 附带一个检查。** 卡里存了一组退路词（有空 / 方便 / 要是 / 不想 / 看你想），候选里一个都没有就判不合格。这是全表里唯一一条"策略允许但写法有硬要求"的规则，因为"只推半步"不是语气问题，是结构问题：不给退路，就等于把拒绝的负担推给她。

**`repairing` 细节密度最低。** 修复期你给的具体信息越多，越像在举证。这是全表里唯一一处"越具体越糟"的地方。

## 4 判定不可靠，这是已知缺陷

阶段是用户自报的，而自报经常不准。三种常见偏差：

- **高报**：认识两周就说"我们在一起了"。按 `couple_early` 处理，会给出过于亲密的候选。
- **低报**：已经天天聊、见过三次，仍说"还没开始"。按 `warming` 处理，会过度谨慎，错过时机。
- **漏报冲突**：明明在冷战，说"就正常啊"。这个最危险，因为 `repairing` 优先级最高，漏掉它等于整条流程失效。

对策不是让模型更聪明，是**给四条硬证据**（她主动发起过吗、单独见过吗、关系说清了吗、有未解冲突吗），让用户自己核对。四条里"有未解冲突"一票否决。

判不准时最省事的做法是直接问一句「你们现在算什么状态」。一句话的成本，远低于按错阶段给出一整套建议。

## 5 迁移检测：只能靠信号，不能靠推理

阶段会变，而且常常在一周内变。系统没有聊天记录权限（这是有意的，见 `safety.md`），所以只能从当次粘贴的片段里找信号。

用的是行为信号，不是情绪推断：

**升**：开始主动发起话题 / 提到未来 / 用内部梗 / 分享不重要的小事

**降**：回复间隔变长且不解释 / 只答不反问 / 连续两次取消且不给替代时间 / 从带语气词变纯陈述

选这些是因为它们**可观察**。"她好像没那么热情了"不可观察，"回复从两小时变两天且不解释"可观察。

降温时最常见的错误反应是提高频率去对冲：她冷，你热，结果是她更冷。正确做法是降一档，用低频、低压、有内容的单条消息维持存在。这条写在 `references/stages.md` 里，因为它是操作规则，不只是设计说明。

## 6 代价

这套设计的代价很明确：**阶段判错的惩罚比没有阶段更重**。

没有阶段时，模型给的是"一般人会怎么回"，平庸但不会错得离谱。判错阶段时，模型会自信地给出一整套方向错误的建议，而且因为每一步都自洽，用户很难发现错在哪。

所以有两条兜底：

1. 判不准就问，不要猜。
2. `guard` 会在候选超出阶段字数上限、用了禁用策略时拦下来。它拦不住"阶段整个判错"，但能拦住最常见的连带错误。

第 2 条是部分缓解，不是解决。真正可靠的做法是用户自己确认一次阶段，然后 `init --stage` 写进档案——那之后每次 `brief` 都会带出阶段任务，不用重新判。
