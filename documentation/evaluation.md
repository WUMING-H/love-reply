# 评测：怎么知道改动是变好还是变坏

这份文档说明 `evals/cases.jsonl` 和 `scripts/eval_skill.py` 在测什么、不测什么、以及为什么这么设计。想加场景可以直接看最后一节，不必读完。

## 问题不是「写得好不好」

这类项目有一个很别扭的特性：**改动的效果立刻可见，损伤却滞后**。

你把 `warming` 的邀约退路规则松一点，当天用起来会觉得「顺畅多了」；两周后你发现对方开始已读不回，但此时你已经改了七版指令，不知道是哪一版埋的雷。没有基线，回滚只能靠记忆。

更麻烦的是，这类项目最常见的失效方式不是报错，是**静默退化**：某个步骤被删掉、某条闸门被放宽、某个策略从「禁止」变成「少用」——系统照常运行，输出看起来也像话，只是下限掉了。用户不会看到异常，只会觉得「最近有点不对劲」。

所以这里需要的不是「评价好坏」，而是「**确认下限还在**」。

## 测什么

评测集是二十六条固定场景，每条包含：

- `stage`：这条对话处在哪个阶段
- `paste`：用户会贴进来的那段话
- `traps`：这条场景容易错在哪（给人看的，不参与断言）
- `good`：三条**应该通过**的候选，标注各自的策略
- `bad`：一到两条**应该被拦下**的候选，标注期望被哪道闸门拦

跑起来做三件事：

1. 每条 `good` 候选都必须通过内容闸门（底线、硬目标、阶段禁用策略、字数）和表达闸门（长度、语气词、AI 味、句号）
2. 每条 `bad` 候选都必须被它声明的那道闸门拦下——没拦住就是「漏放」，说明闸门变松了
3. 用例本身也在被检验：好候选少于三条、三条策略不互斥、阶段名拼错、id 重复，都算失败

外加覆盖率断言：六个阶段、六种策略都必须有用例。加场景时容易只盯着自己最近遇到的阶段，覆盖率会悄悄塌陷。

## 高危路径：以前一条用例都没有

`danger ≥ 7 只允许稳住 / 补救 / 留白` 是这套东西里唯一涉及人身安全的规则。而在 0.11.0 之前：`guard()` 没有 `danger` 参数，26 条用例里 `danger` 出现 0 次，没有任何断言会因为它失效而变红。

也就是说，最该被守住的一条，恰好是唯一没有人看守的一条。原因是它长得像「语义判断」——确实，`danger` 打几分只能靠模型读对话。但**打分是人给的，拦截不一定要靠人**：只要 `danger` 作为参数传进闸门，「7 分以上不许邀约」就是一句可以机械执行的话。

现在的写法：

- `verify --danger 7`，≥7 时 `advance`、`substantive` 直接 fail，`minimal`、`care`、`repair`、`hold` 放行。
- `evals/cases.jsonl` 补了两条高危用例（自伤、威胁），各配一条该被拦的候选。
- 评测增加覆盖断言：**没有一条 `danger≥7` 的用例就失败**。用例被删掉时，这条断言比用例本身更重要。

顺带记一个教训：`danger` 只在提示词里出现过，所有测试都是绿的，文档也写着「这是硬约束」。**提示词里的规则和代码里的规则，是两种东西**——前者靠模型记得，后者靠断言。分不清这两者，就会以为有保障。

## 不测什么

**不测「这句话回得妙不妙」。**

这是刻意的。任何让模型给自己打分的评测，都会得到一个漂亮的分数和一个没用的结论：模型对自己的输出有系统性偏袒，同样的输入两次评分能给两个答案，改坏了也未必看得出来。而这种不可复现的数字，比没有数字更危险——它会让人误以为有保障。

语义层面的东西，比如「她说的『随便你』是反话，`minimal` 那句『那你早点睡』接了字面」，机械断言判断不了。这类场景的写法是：把**能机械判定的部分**声明出来（比如修复期不许出现邀约句式），把**判断意图**写进 `traps` 字段留给人看。

所以这份评测的定位是：**它能阻止变坏，不能证明变好**。变好要靠真实使用，或者盲测——把五句自己打过的话混进五句改写，逐条判「这是我打的吗」，猜中率才能真正说明风格层有没有起作用。

## 盲测：补上「变好」这一半

做法很笨：拿八到十五条你自己真打过的话，配上同一场景的改写，左右随机打乱，逐条问「哪句是你打的」。不用评价好坏，只需要认领自己的话。**认不出来的比例，就是风格层起作用的程度。**

```bash
python scripts/blind_test.py make  --in lines.jsonl --out rounds/r1 --seed 7
python scripts/blind_test.py score --round rounds/r1 --picks "B,A,B,-,A,A,B,A,B,B"
```

`make` 产出两个文件：`sheet.md`（只有 A/B 两句话，给人判）和 `key.json`（答案）。分开是刻意的，因为**这套东西唯一有效的理由，就是判的时候看不见答案**。

`lines.jsonl` 不是 `evals/cases.jsonl`。后者是喂给闸门的，字段是 `good` / `bad`；盲测要的是 `mine`（你真发出去的那句）和 `generated`（改写）。忘了格式就跑 `python scripts/blind_test.py template`，它会打一条骨架出来。

### 为什么不用相似度

用 `difflib` 直接算改写和原话的相似度，看起来更省事，方向却是反的：一个只把「行」改成「好」的改写相似度最高，而它恰恰是最没用的那种改写——什么都没改掉，只是换了个字。**相似度奖励偷懒。** 人能不能认出自己的话，奖励的是「这个说法我会用」。

脚本里也确实用到了 `difflib`，但只用来**剔除**相似度 ≥0.85 的条目（几乎没改写的样本，答对答错都说明不了问题），不参与评分。

### 为什么是精确二项检验

n 通常只有八到十五条。这个量级上用正态近似，会把「八条全对」算成一个不够吓人的 p 值：精确值 1/256 ≈ 0.0039，近似给到 0.0078 上下。小样本的时候，近似不是省事，是给出错的结论。所以直接对二项分布求和，`math.comb` 就够，不需要任何依赖。

### 三个作废条件

写在 `score` 里，不靠人自觉：

| 条件 | 为什么 |
| --- | --- |
| 有效条数 < 8 | 八条对七条 p=0.035，对六条 p=0.145。样本不够时，任何比例都能被解释成任何结论 |
| 同一侧 ≥85% | 侧向偏好。人一旦开始按位置点，答案就与内容无关，此时任何认出率都是噪声 |
| 认出率 ≤20% | 系统性认错。要么偷看了 `key.json`，要么在照长短猜，两种都不算数 |

退出码：`0` 分不出来（通过）、`1` 能分辨（红灯）、`2` 无法判定（样本不足 / 作废 / 反常）。

### 和评测集的分工

评测集跑在 CI 里，每次提交都跑，管的是「不许变坏」，所以它必须固定、机械、离线。盲测跑在人身上，一次十来条，管的是「有没有变好」，所以它必须有真人、必须看不见答案、必须承认样本小。**前者防回归，后者定方向。** 混在一起做的结果，通常两边都做不好。

### 它会顺带说出别的事

「改写平均比你原话长 1.6 倍」——风格卡的长度档位和你的真实发言脱节了。「一半条目被误认成自己，但位置分布极度偏斜」——这次测试本身失效了，结论别用。这些都不进评分，只进输出。数字之外的那句话，往往比数字有用。

## 为什么用固定候选，而不是现场生成

现场生成听起来更「真实」，但会引入三个不可控变量：模型版本、采样温度、上下文残留。任何一次失败都分不清是规则坏了还是这次运气不好。

固定候选把变量掐死：同样的输入永远同样的结论。这样它才能在 CI 里跑，才能在你改了一行闸门之后立刻告诉你「有两条例外漏出去了」。

代价是它只能覆盖「闸门对已知样本的反应」，覆盖不到「模型实际会生成什么」。这个缺口由真实使用来补——遇到一次坏输出，就把它补成一条 `bad` 用例。评测集应该随着踩坑慢慢长大，而不是一次写全。

## 变异测试：确认它真的会失败

一个永远绿的测试等于没有测试。所以这套用例做过变异验证——在临时副本里故意改坏闸门，看评测会不会红：

| 变异 | 期望 | 实际 |
| --- | --- | --- |
| `repairing` 的 `deny` 从 `["advance"]` 改成空 | 修复期的邀约候选漏放 | `r1`、`r4` 漏放，退出码 1 |
| `HIGH_RISK` 去掉「呢」 | 「我记着呢」不再被拦 | `t2` 漏放，退出码 1 |
| 删掉 `SKILL.md` 的「改风格」整段 | 完整性检查报错 | 三条错误点名，退出码 1 |

第一条最值得说：如果评测只是「拿一批候选去跑当前实现，然后记录结果」，那它永远绿，改坏了也绿。**能红的才算测试。**

## 它抓过的真问题

第一版跑起来红了三条。其中两条是用例自己写错（长度算错），一条是闸门错了：

`d3` 场景里，用户被问「你是不是对谁都这样」，最自然的一字回答是「没有」。风格闸门判它「太短：2 字，目标 ≥3，可能丢了信息」。

问题在 `lo = 3` 这个数——它是没有风格卡时拍的。而两字回复在中文聊天里是最高频的答法：「没有」「不去」「好啊」「在的」。逼模型把「没有」改成「我没有啦」不是变好，是失真。

改成 `lo = 1`：没有风格卡就没有下限依据，唯一该拦的是空字符串。这个 bug 存在了很久，因为没有任何测试会去构造一个两字候选——人写用例时，下意识会写得像一条「完整的句子」。

## 退出码：2 有三种含义

| 命令 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| `validate_skill.py` | 全部通过 | 有硬错误 | 只有警告（**仍算通过**） |
| `eval_skill.py` | 全部通过 | 有用例失败 | — |
| `profile_tool verify` | 全过、闸门也跑过 | 参数错误 | 有候选没过 / 成组不合格 / 阶段闸门没跑 / 续写缺 `--prev` |
| `blind_test.py score` | 分不出来 | 能分辨 | 无法判定 |

别写 `if code: 失败` 一把抓：`validate` 的 2 是「通过，但值得看一眼」，`verify` 的 2 是「这组不能发」。混着判，要么把警告当故障，要么把故障当警告。

## 加一条场景

往 `evals/cases.jsonl` 追加一行即可，不改代码：

```json
{"id":"c5","stage":"couple_early","paste":"她：算了 不说了","traps":"撤诉不是解决",
 "good":[{"strategy":"minimal","text":"别算了 你说"},
         {"strategy":"care","text":"你这句让我有点慌"},
         {"strategy":"repair","text":"是我刚才那句让你不想说了"}],
 "bad":[{"strategy":"advance","text":"那明天见面说清楚","gate":"content","why":"修复期禁止推进"}]}
```

字段说明：

- `gate`：`content`（内容闸门）、`style`（表达闸门）、`term`（术语表）、`either`（任一即可）
- `facts` / `goals` / `self`：可选，用来给这条场景挂上档案片段，验证硬目标和自我底线
- `traps`：不参与断言，写给下一个人看

写完跑一遍：

```bash
python scripts/eval_skill.py -v
```

`-v` 会逐条打印通过的候选和被拦的候选，方便确认断言真的落在了你预期的位置，而不是碰巧通过。

## 什么时候该动它

- **踩到一次坏输出**：把那段对话和当时的错误候选补成用例。这是最有价值的来源。
- **调整闸门参数**：先跑一遍，确认改动只影响目标场景，没有顺手放过别的。
- **新增阶段或策略**：覆盖率的断言会立刻报错，这是设计上的提醒——新东西没有被测到。

不要为了「让评测通过」去改用例里的候选。用例红了，先判断是闸门错了还是候选错了；两者都可能是真问题，但把候选改到能过，等于把测试变成橡皮图章。
