# trace：把一次决策记下来，事后查得清

## 为什么需要它

模型产出候选时，其实做了一串决定：判了什么阶段、什么意图、danger 打几分、取了哪几篇知识、写了什么策略、过闸拦了什么。这些决定平时散在一次次调用里，没人汇总。

后果是：**候选看着没问题，但你不知道它是怎么得出来的**。想改进时，只能靠猜——是阶段判错了，还是取了篇不对的知识，还是过闸漏了？猜不出来。

`trace` 把这串决定收成一段记录，再对照已经建好的规则查「自不自洽」。它不调模型，是事后可追溯的确定性校验。

## 怎么用

```bash
python scripts/profile_tool.py trace --json '{
  "stage": "couple_early",
  "intent": "vent",
  "danger": 3,
  "strategies": ["care", "repair"],
  "kb_files": ["references/kb/practical/为他人提供情绪价值：温暖且有效的回应指南.md"],
  "verify": {"verdict": "pass"}
}'
```

或者存成文件再喂：

```bash
python scripts/profile_tool.py trace --file trace.json
```

输出 `ok: true/false` + `problems`（哪里不自洽）+ `notes`（要留意但不算错）。退出码 0 表示自洽，1 表示有矛盾。

## 字段

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `stage` | 判出来的阶段，六档之一 | 判阶段那一步 |
| `intent` | 判出来的意图，六选一 | 判意图那一步 |
| `danger` | 危险度 0–9 | 判危险那一步 |
| `strategies` | 最终候选用的策略（可多条） | 写候选那一步 |
| `kb_files` | 实际读的知识篇目路径 | 取知识那一步 |
| `verify` | 过闸结果（`verdict`） | 过闸那一步 |

`strategies` 填的是策略名，不是候选原文——trace 查的是「决定对不对」，不是「句子好不好」。句子好不好由盲测和端到端清单管。

## 查什么

四件事，对应四步最容易错的地方：

1. **阶段闸门**：阶段拼错、或用了该阶段禁止的策略（比如 repairing 给 advance）。
2. **danger 阈值**：danger≥7 却给 advance / substantive——这时候只该稳住或补救。
3. **知识路由**：取的篇目是不是真能被「意图 × 阶段 × danger」路由出来，取错了一眼看得出。
4. **过闸一致性**：verify 报 pass，但上面的矛盾没查出来——说明过闸和记录对不上，这个 pass 不能采信。

## 边界

- trace **不进候选输出**。候选的格式红线照旧：不输出 JSON、不输出阶段名、不输出心理学名词。trace 是后台记录，用户想看才看。
- trace 查的是「决策链自洽」，不是「决策正确」。判错阶段但判的确实是六档之一，trace 不会报错——它只报「自相矛盾」，不报「判断错了」。
- 想让 trace 有用，得**真的把每一步的决策填进去**。填得越全，事后越查得清；糊弄着填，trace 就是摆设。
